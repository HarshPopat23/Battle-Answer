1. COMPLIANCE COMPARISON
Constraints: 1 app instance, multiple worker processes, PostgreSQL exists, no Redis/Kafka/paid services, concurrent claims, crash after external side effect before recording success, bounded retries, durable recovery, observability.

A. In-memory queue:
- Fails durability: a crash or process restart loses all queued and in-flight work.
- Fails recovery: no way to recover jobs after crash.
- Fails if app instance restarts; not durable.
- Only advantage is speed, which is unnecessary here. REJECTED on durability/recovery.
B. PostgreSQL-backed job table:
- Durable (WAL), atomic claims via transactions, no extra service. Satisfies all constraints assuming correct lease/expiry design. COMPLIANT.
C. Redis-backed queue: violates the explicit 'No Redis' constraint. Even if allowed, shared-state queues outside Postgres do not give you the same transactional boundary with the job state. REJECTED on compliance.

CHOSEN: B.
2. MINIMAL TABLE FIELDS AND USEFUL INDEXES
CREATE TABLE jobs (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  job_type TEXT NOT NULL,
  payload JSONB NOT NULL DEFAULT '{}'::jsonb,
  idempotency_key TEXT UNIQUE,           -- dedupe requests; NULL allowed if job is internally generated
  state TEXT NOT NULL DEFAULT 'queued' CHECK (state IN ('queued','leased','failed','succeeded','dead')),
  attempts INT NOT NULL DEFAULT 0,
  max_attempts INT NOT NULL DEFAULT 3,
  run_at TIMESTAMPTZ NOT NULL DEFAULT now(),   -- next eligible run time (backoff)
  lease_token UUID,                        -- unique per claim, used to fence stale completions
  lease_expires_at TIMESTAMPTZ,            -- when the lease lapses
  worker_id TEXT,                          -- observability: which worker claimed it
  last_error TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  succeeded_at TIMESTAMPTZ
);
Useful indexes:
- Partial index on claimable jobs: CREATE INDEX jobs_claimable ON jobs (run_at) WHERE state = 'queued' AND run_at <= now();
- Index on (id) is PK. Consider (state, run_at) for recovery scans: CREATE INDEX jobs_recovery ON jobs (state, lease_expires_at) WHERE state = 'leased';
- Unique index on idempotency_key (already from UNIQUE constraint).
Notes/assumptions (not verified): partial index + UPDATE ... WHERE id IN (...) FOR UPDATE SKIP LOCKED is supported in Postgres; verify SKIP LOCKED behavior (introduced in 9.5) against the actual server version before relying on it.
3. ATOMIC CLAIM SQL AND TRANSACTION BOUNDARIES
Claim (per worker, in a single short transaction):
BEGIN;
  WITH pick AS (
    SELECT id FROM jobs
    WHERE state = 'queued' AND run_at <= now()
    ORDER BY run_at, id
    LIMIT 1
    FOR UPDATE SKIP LOCKED
  )
  UPDATE jobs j
     SET state = 'leased',
         lease_token = gen_random_uuid(),
         lease_expires_at = now() + interval '30 seconds',
         worker_id = current_setting('app.worker_id'),
         attempts = attempts + 1,
         updated_at = now()
    FROM pick
   WHERE j.id = pick.id
  RETURNING j.id, j.job_type, j.payload, j.idempotency_key, j.lease_token, j.attempts;
COMMIT;
Transaction boundary rules:
- The claim must be its own tiny transaction, committed before doing any external side effect. Never hold the row lock while performing the external call.
- Use FOR UPDATE SKIP LOCKED so concurrent workers skip rows others are claiming; this is proposed behavior — must be verified against the actual Postgres version.
- set app.worker_id via SET LOCAL within the transaction for observability.
- If zero rows returned, the worker should sleep briefly and loop; do not retry in an unbounded hot loop.
4. LEASE EXPIRY, RECOVERY, STALE-WORKER HANDLING
- lease_expires_at = now() + lease_duration (e.g. 30s) at claim time, longer than the worst-case external call time.
- Recovery loop (separate worker/heartbeat or one worker designated as reaper):
    UPDATE jobs
       SET state = 'queued', lease_token = NULL, lease_expires_at = NULL, worker_id = NULL, updated_at = now()
     WHERE state = 'leased' AND lease_expects_at IS NOT NULL AND lease_expires_at < now();
  (Reaper sets state back to 'queued' so it can be claimed again.)
- Stale-worker fencing: every completion/advance operation requires the original lease_token: e.g.
    UPDATE jobs SET state='succeeded', succeeded_at=now() ...
     WHERE id=$1 AND lease_token=$token;
  If a stale worker (which didn't actually hold the lease because it expired and was re-claimed) tries to record state, the UPDATE matches 0 rows. All state transitions must be conditional on the lease_token to prevent a crashed-then-revived worker from corrupting state. This fencing is proposed; correctness depends on consistent use and must be tested.
- Idempotency of recovery: making a lease expired and re-queued is naturally idempotent because it's keyed on state + timestamp.
5. BOUNDED RETRIES, BACKOFF, TERMINAL FAILURE
- attempts increments on claim. max_attempts defaults to 3.
- On failure between external call and commit: worker updates jobs to state='failed' with run_at = now() + backoff(attempts), keeping lease check.
  - If attempts < max_attempts: state='queued', run_at backoff, attempts preserved.
  - Backoff: run_at = now() + (base * 2^(attempts-1)) with jitter, e.g. base=10s: 10s, 20s, 40s...
- Terminal failure (dead): when attempts >= max_attempts after a failure path, set state='dead', last_error set, updated_at=now(). These are not retried and are reportable.
- Important sub-case (the one in the requirements): the worker completes the external side effect but crashes before recording success. If the lease has NOT expired, the job is still 'leased' and will be re-queued on lease expiry and retried (risking duplicated side effect — addressed by idempotency in section 5 of task/section below). If the lease has expired and the state was never advanced, the reaper re-queues it; subsequent processing must be idempotent.
- Every failure path writes last_error and persists to keep observability.
6. IDEMPOTENCY KEYS AND DEDUPLICATION OF EXTERNAL SIDE EFFECTS
- idempotency_key column, UNIQUE: for externally initiated jobs, derive a key from the originating request (e.g. RFC 4123 UUID sent by client, or hash of (request_id, action)).
- On ingest, INSERT ... ON CONFLICT (idempotency_key) DO NOTHING; duplicate submits are dropped, so a request is never enqueued twice.
- Before performing the external side effect, the worker checks/records a dedupe outcome (a separate idempotent-effect table or a marker within the external system via the key). Key point: the external side effect must be made idempotent by passing the idempotency_key to the external system so repeated executions (from retry after crash) do not duplicate the effect.
- Design principle: exactly-once at the external system boundary is generally UNACHIEVABLE from the Postgres side alone; the practical guarantee is at-most-once execution per launch path plus idempotent-effect design + dedupe, giving effective exactly-once observable outcomes. This is a proposed invariant, not verified.
7. CRASH TIMELINE — WHY A POSTGRES TRANSACTION DOES NOT GUARANTEE EXACTLY-ONCE EXTERNAL EFFECTS
Assume single worker claims job J:
  t0  BEGIN; claim J (state=leased, lease_token=T1). COMMIT.        -- Postgres durably records 'leased' + token T1
  t1  Worker performs external side effect S (payment charge, HTTP POST, etc.). The external system commits independently. [External effect persisted outside Postgres.]
  t2  Worker crashes (power loss, OOM, segfault) BEFORE issuing the 'UPDATE jobs SET state=succeeded' transaction.
  t3  (optionally) lease expires; reaper re-queues J.
  t4  A worker re-claims J (lease_token=T2) and performs S again.
Why not exactly-once: The external effect S at t1 and the Postgres success record are two separate, non-atomic systems. The Postgres transaction at t0 only covers the claim; the success transaction never executes because of the crash at t2. Because nothing in Postgres recorded that S was executed, a re-run at t4 blindly executes S again. The Postgres transaction cannot atomically include the external side effect, so an external exactly-once guarantee cannot be derived from it. The only robust mitigations are: make S idempotent (via idempotency_key checked in the external system) and re-check dedupe before acting — i.e. at-least-once jobs + idempotent effects = effectively exactly-once outcomes. This is proposed; the specific step t1/t2 interleaving must be reproduced in a test to be verified.
8. REMAINING RISK AND TEST STRATEGY
Remaining risks:
- Duplicate external side effect between a stale (crashed) worker finishing a lease-expired job and the re-claimer: both might call S. Mitigation: lease duration must exceed total external call time; PLUS idempotency_key at the external system; PLUS fencing updates require lease_token. Residual risk exists if a stale worker and the re-claimer run in true parallel while the lease is expiring — must verify lease lengths and test it.
- Repeated lease flip-flops if external call takes close to the lease duration: tune lease to comfortably exceed worst-case.
- Exactly-once unavailable by design: it is effectively at-least-once + idempotence; do not claim exact-once.
- Pagination/fairness on high load: SKIP LOCKED with ORDER BY run_at, id can starve; acceptable at single-instance scale.
- Poison jobs (always fail) burn the max_attempts budget; dead-letter to a dead state and alert.
- Clock skew between workers and DB: use DB now() (clock from one source) rather than app-side clock in lease math.
Tests to run (proposed plan; not executed because no code/database is present in this workspace):
- Unit: claim returns exactly one row when N workers claim simultaneously (needs a live Postgres, SKIP LOCKED path).
- Lease expiry: a job leased, with lease set in the past, is re-queued by the recovery update.
- Stale fencing: an UPDATE with an old lease_token matches 0 rows; one with the current token matches 1 row.
- Bounded retries: a job that always fails transitions queued→leased→queued (backoff) and reaches dead after max_attempts.
- Idempotency: two identical submits with the same idempotency_key produce one row (ON CONFLICT DO NOTHING).
- Crash-simulation for section 7: claim, simulate external effect, then kill (SIGKILL) the worker, verify state remains leased then re-queue, then re-run and observe the side effect ran twice — confirming exactly-once is not provided, only idempotency protects outcome correctness.

Summary: Option B (PostgreSQL job table) is the only fully compliant choice. It provides durability via WAL, atomic claims via a single short transaction with FOR UPDATE SKIP LOCKED, recovery via lease expiry and a reaper, terminal failure via a bounded 'dead' state, deduplication via a unique idempotency_key and an idempotent external call. Exactly-once external effects are NOT derivable from a Postgres transaction; the design achieves at-least-once job execution plus idempotent external effects, giving effective exactly-once observability. All Postgres-specific lock/fence statements are proposed and require validation on a live database; no experimental verification was performed in this workspace.
